# Telegram Kids — архитектурные решения

## Почему TDLib (не GramJS, не Telethon на мобиле)

TDLib — официальная C++ библиотека Telegram, используется во всех официальных клиентах.
Медиафайлы (фото, видео, аудио, кружочки) идут НАПРЯМУЮ между телефоном и Telegram CDN.
Через наш сервер проходят только события управления (вступил в чат, написал боту).

GramJS отклонён: нестабилен при обновлениях MTProto, требует полифиллов в RN.
Telethon на сервере как прокси: двойной трафик, дорого, медленно.

## Архитектура под масштаб (с первого дня)

```
[Устройства детей]
  TDLib ←→ Серверы Telegram (медиа, сообщения — наш сервер не видит)
  React Native UI
  HTTPS (stateless POST) ←→ Load Balancer → API серверы
  FCM listener           ←  Firebase (push от сервера к ребёнку)

[Load Balancer — nginx]
  Распределяет запросы между инстансами API

[API серверы — N инстансов, STATELESS]
  FastAPI, без asyncio.Event, без состояния в памяти
  Любой инстанс обрабатывает любой запрос
  Пишут в PostgreSQL, читают из Redis-кэша

[PostgreSQL]  [Redis]        [Firebase Admin SDK]
  БД            кэш сессий,    FCM push → Android
                rate limits,   APNs push → iOS
                pending reqs

[Телефон родителя]
  Обычный Telegram + наш бот (python-telegram-bot)
  Получает push через Telegram (не FCM — родителю бот пишет)
```

### Почему не WebSocket

WebSocket = постоянное соединение в памяти сервера.
1000 детей онлайн = 1–2 ГБ RAM только на соединения.
При падении сервера — все соединения теряются.

FCM (Firebase Cloud Messaging):
- Сервер полностью stateless — нет памяти о соединениях
- Firebase гарантирует доставку (retry, offline queuing)
- Масштабируется до миллионов устройств без изменений кода
- Бесплатно до 1 млн сообщений/месяц

### Флоу запроса на разрешение (через push)

```
1. Ребёнок пытается вступить в чат
2. POST /request-approval → создаёт pending_request в БД
                          → возвращает {request_id} немедленно
3. Сервер → Telegram бот → родитель получает уведомление
4. PendingScreen показывается, опрашивает GET /request-status/{id} раз в 3 сек
   (лёгкий polling пока ждём — соединение НЕ висит открытым)
5. Родитель нажимает Разрешить/Запретить в боте
6. Сервер обновляет статус в БД
7. Сервер → Firebase → FCM data message → телефон ребёнка
8. Приложение получает push → PendingScreen мгновенно обновляется
   (если приложение в фоне — OS показывает уведомление)
```

### Серверная нагрузка при FCM-архитектуре

| Ресурс | 1К детей | 10К детей | 100К детей |
|---|---|---|---|
| RAM | ~256 МБ | ~512 МБ | ~2 ГБ (2–3 инстанса) |
| Трафик | < 1 ГБ/мес | < 10 ГБ/мес | < 100 ГБ/мес |
| Стоимость сервера | $10/мес | $40/мес | $150/мес |

## TdLib.js — главный принцип

Singleton. Все взаимодействия с TDLib ТОЛЬКО через него.
Экраны не вызывают TDLib напрямую — только через store или hooks.

```js
// Правильно:
const chats = useChats()  // Zustand store, данные уже там

// Неправильно:
TdLib.send({ '@type': 'getChats' })  // не из экрана напрямую
```

TdLib.js обрабатывает ВСЕ обновления (updateNewMessage, updateChatLastMessage и т.д.)
и пишет их в Zustand store. Экраны только читают store.

## Zustand store — структура

```js
// store/auth.js
{ status: 'unauthorized'|'wait_code'|'wait_password'|'ready', user: {...} }

// store/chats.js
{ chats: Map<chatId, Chat>, order: chatId[], loading: bool }

// store/messages.js
{ messages: Map<chatId, Message[]>, loading: Map<chatId, bool> }

// store/ui.js
{ theme: 'dark'|'light', pendingRequests: [] }
```

## Родительский контроль — точки перехвата в мобильном приложении

При попытке ребёнка сделать что-то ограниченное:
1. TdLib.js перехватывает событие ДО выполнения
2. Отправляет запрос на наш сервер через WebSocket
3. Показывает PendingScreen (ожидание решения родителя)
4. Сервер уведомляет родителя через бота
5. Родитель жмёт Разрешить/Запретить
6. Сервер отвечает через WebSocket
7. PendingScreen закрывается, действие выполняется или блокируется

Точки перехвата:
- Вступление в новый чат/канал → проверка перед joinChat
- Начало переписки с незнакомым → проверка перед первым сообщением
- Добавление бота → проверка перед открытием

## Дизайн-система

**Принцип:** UX-паттерны Telegram (расположение, жесты, навигация) + собственная визуальная идентичность.
UX-паттерны авторским правом не защищаются. Логотипы и иконки Telegram — не используем.

**Цвета:**
```
Фон основной:        #17212b
Фон вторичный:       #0e1621
Фон элементов:       #1e2d3d
Акцент (наш):        #2E86AB   ← не Telegram blue (#5288c1)
Пузырь входящий:     #182533
Пузырь исходящий:    #1B5E8A
Текст основной:      #ffffff
Текст вторичный:     #aaaaaa
Разделитель:         #2b3a4a
```

**Иконки:** Material Icons (Google, Apache 2.0) — не иконки Telegram.
**Логотип:** свой (создать отдельно — щит + силуэты детей).
**Шрифт:** системный (SF Pro / Roboto).

**Remote Theming — цвета, шрифты, иконки из БД:**
Все визуальные параметры хранятся в таблице `app_themes` на сервере.
Приложение загружает тему через `GET /theme` при старте, кэширует в MMKV.
Смена темы в БД → все пользователи видят изменение без обновления приложения.
Компоненты получают тему ТОЛЬКО через `useTheme()` — никакого хардкода цветов.

**Расположение элементов — как в Telegram:**
- Список чатов: главный экран, вертикальный список
- Переписка: пузыри, поле ввода внизу, кнопка отправки справа
- Stories: горизонтальная лента вверху ChatsScreen
- Таб-бар: снизу (Чаты / Контакты / Настройки)
- Свайп влево по чату: архив/удалить
- Long-press на сообщении: реакции + меню

## Кэширование файлов и медиа

**TDLib берёт на себя полностью:**
- Кэш аватаров, миниатюр, стикеров, GIF
- Возобновляемые загрузки (resume при обрыве сети)
- Дедупликация (один файл не скачивается дважды)
- Автоматическое удаление старых файлов при нехватке места
- Приоритеты загрузки (открытый чат качается первым)

**Мы настраиваем один раз при инициализации TDLib:**
- `setOption storage_max_files_size` — лимит кэша (дефолт: 1 ГБ)
- `setAutoDownloadSettings` для WiFi: фото до 10 МБ, видео до 15 МБ
- `setAutoDownloadSettings` для мобильного: только фото до 5 МБ

**Мы реализуем только UI:**
- Прогресс загрузки: слушаем `updateFile` в TdLib.js → пишем в store
- Экран «Настройки хранилища»: `getStorageStatistics` + `optimizeStorage`
- Переключатели авто-загрузки в Настройках (Фаза 5)

Никакого собственного кэша изображений поверх TDLib не нужно.
`react-native-fast-image` используем только для загрузки аватаров
по URL (не через TDLib) — например, аватар родителя в боте.

## Бэкенд — важные детали

- Согласие с политикой: DOI (два клика: бот + ссылка в email)
- Все согласия хранятся с текстом и датой (152-ФЗ)
- Rate limiting: 3 OTP/10мин по IP, 5 писем/сутки, 1 «Готово»/2мин
- Event-based ожидание: asyncio.Event, сервер держит соединение открытым
- Таймаут ожидания решения родителя: 10 минут
- БД: SQLite сейчас, миграция на PostgreSQL при > 1000 пользователей

## ⚠️ ГЛАВНЫЙ ПРИНЦИП: изменения без риска сломать код

> Читать в начале КАЖДОЙ сессии. Любое новое решение проверять по этому списку.

### 1. Никогда не трогать работающий код — только добавлять

```
ПЛОХО:  изменить существующую функцию чтобы добавить фичу
ХОРОШО: написать новую функцию, старую оставить нетронутой
```

Если нужно изменить поведение — создать новый модуль/хук/компонент,
старый убрать только когда новый проверен в проде.

### 2. Слои — каждый слой зависит только от нижнего

```
Экраны (screens/)          — только вызывают hooks, не знают о TDLib и API
    ↓
Хуки (hooks/)              — читают store, вызывают actions
    ↓
Store (store/)             — Zustand, единственный источник истины
    ↓
Сервисы (TdLib.js, api.js) — единственная точка входа к TDLib и серверу
    ↓
Нативный модуль / HTTP     — железо и сеть
```

Нарушение этого порядка = риск сломать при рефакторинге.

### 3. Один файл — одна ответственность

- `TdLib.js` — ТОЛЬКО связь с TDLib, никакой UI-логики
- `api.js` — ТОЛЬКО HTTP/WebSocket к нашему серверу
- `useTheme.js` — ТОЛЬКО тема, никаких других данных
- Экраны — ТОЛЬКО рендер, никаких прямых вызовов TDLib/fetch

### 4. Feature flags для всего нового

Каждая новая крупная фича включается через флаг в БД (`feature_flags` таблица).
Если фича сломана — выключаем флаг, приложение работает без неё.

```sql
feature_flags: name, is_enabled, description
-- stories, video_notes, reactions, calls, stickers_animated
```

```js
const { isEnabled } = useFeatureFlag('stories')
if (!isEnabled) return null   // экран просто не показывается
```

### 5. Fallback для каждого внешнего вызова

```js
// Тема: если сервер упал — используем встроенную дефолтную
// TDLib: если метод вернул ошибку — показываем graceful error, не краш
// API: если таймаут — возвращаем кэшированные данные из MMKV
```

### 6. Backward compatibility в API

При изменении ответа эндпоинта:
- Добавлять новые поля можно (мобильный их проигнорирует)
- Удалять или переименовывать поля нельзя без версионирования
- Мобильный всегда читает поля через `?.` (optional chaining)

```js
// Правильно:
const name = chat?.title ?? chat?.name ?? 'Без названия'
// Неправильно:
const name = chat.title  // упадёт если title переименуют
```

### 7. Состояние только через store, никакого prop drilling

Данные из TDLib → store → хуки → компоненты.
Никогда: компонент А передаёт данные компоненту Б через props на 3+ уровней.

### 8. Проверка перед любым изменением существующего модуля

Перед правкой файла который уже работает — ответить на три вопроса:
1. Что ещё зависит от этого файла? (поиск `import` в проекте)
2. Можно ли добавить новое не трогая старое?
3. Есть ли fallback если новый код упадёт?

## Обработка ошибок

Три уровня — выбирать минимально достаточный:

| Ситуация | Реакция |
|---|---|
| Нет сети при запуске | Показать кэшированные данные + баннер «Офлайн» |
| Нет сети при действии | Toast «Нет соединения», не блокировать UI |
| TDLib вернул ошибку | Graceful error в компоненте, не краш приложения |
| Неожиданный краш | Error Boundary → экран «Что-то пошло не так» + кнопка «Перезапустить» |
| 401 от нашего сервера | Тихо переавторизоваться, повторить запрос |
| 5xx от нашего сервера | Retry 3 раза с backoff, потом показать ошибку |

```js
// Каждый экран оборачивается в ErrorBoundary
// Каждый async-вызов имеет try/catch с конкретным fallback
// Никогда: пустой catch без обработки
```

## Офлайн-режим

Приложение должно быть полезным без сети (мессенджер часто открывают без связи).

- **При старте без сети:** показать последние чаты и сообщения из MMKV-кэша
- **При потере сети в процессе:** продолжить показывать кэш + индикатор офлайна вверху
- **Отправка сообщения офлайн:** поставить в очередь (store/outbox.js), отправить когда сеть появится
- **Медиа офлайн:** показывать превью из кэша, не пытаться загрузить

```js
// NetInfo из @react-native-community/netinfo — слушать статус сети
// При reconnect: синхронизировать outbox, обновить чаты
```

Кэшировать в MMKV: последние 50 чатов, последние 30 сообщений каждого активного чата, все загруженные аватары.

## Безопасность

**Что никогда не хранить на устройстве ребёнка:**
- Пароль / 2FA код в открытом виде
- Токен авторизации в AsyncStorage без шифрования → использовать MMKV с encryption key

**Что никогда не логировать:**
- Содержимое сообщений
- Номер телефона полностью (только последние 4 цифры в логах)
- Токены и сессии

**TDLib сессия:**
- Хранить StringSession в MMKV с шифрованием
- При выходе — вызвать `logOut` в TDLib и очистить MMKV

**Наш сервер:**
- Токен ребёнка в заголовке `x-api-key` — только HTTPS
- WebSocket — только WSS

**Детское приложение — дополнительно:**
- Нет возможности отключить родительский контроль из приложения
- Нет возможности удалить историю запросов на разрешение
- Screenshot prevention на экране ввода кода (опционально)

## Производительность

React Native легко замедлить на бюджетных телефонах. Обязательные правила:

**FlatList:**
```js
// Всегда указывать:
keyExtractor={item => String(item.id)}
getItemLayout={(_, index) => ({ length: 72, offset: 72 * index, index })}
maxToRenderPerBatch={10}
windowSize={5}
removeClippedSubviews={true}
// Никогда не использовать ScrollView для списков > 20 элементов
```

**Изображения:**
- Только `FastImage` (react-native-fast-image), не `Image` из RN
- Аватары: кэшировать бессрочно (они не меняются часто)
- Медиа в чате: кэшировать 7 дней, потом удалять

**Анимации:**
- Только `Reanimated 3` — работает на нативном потоке
- Не `Animated` из RN — работает на JS потоке, лагает

**TDLib события:**
- Обновления из TDLib могут приходить очень часто (сотни в секунду при синхронизации)
- Писать в store через `batch` (Zustand поддерживает)
- `updateFile` — дебаунсить 100ms, иначе перерисовка на каждый байт загрузки

**Память:**
- Выгружать сообщения чатов которые не открыты > 5 минут (оставлять только первые 30)
- Не хранить в памяти больше 200 чатов одновременно

## Порядок запуска приложения

Строгая последовательность — нарушение вызовет краш:

```
1. MMKV инициализация (синхронная, первая)
2. Загрузка кэша темы из MMKV → применить до рендера
3. Загрузка feature flags из MMKV (кэш)
4. TdLib.initialize() → нативный модуль
5. Проверка сохранённой сессии TDLib
   ├── Есть сессия → TdLib.connect() → authorizationStateReady
   │   └── Загрузить чаты из кэша → показать ChatsScreen
   └── Нет сессии → показать LoginScreen
6. В фоне (после показа UI):
   ├── GET /theme → обновить тему если изменилась
   ├── GET /feature-flags → обновить флаги
   └── GET /auth/status → проверить привязку к родителю
```

Если TdLib.initialize() падает — показать экран ошибки, не пытаться продолжить.

## Что приложение ребёнка отправляет на наш сервер

**Отправляется (необходимо для родительского контроля):**
- Попытка вступить в новый чат → `chat_id`, `chat_title`
- Попытка написать новому боту → `bot_username`
- Попытка начать переписку с новым контактом → только факт (не содержимое)
- Статус привязки (привязан / не привязан)
- FCM/APNs токен устройства (для push-уведомлений)

**НЕ отправляется никогда:**
- Содержимое сообщений
- Медиафайлы
- Список всех контактов
- История переписки
- Геолокация

Это фиксируется в Политике конфиденциальности (уже написана, хранится в БД).

```
main          — стабильный код, всегда работает
```

- PATCH: баг-фиксы (1.0.1)
